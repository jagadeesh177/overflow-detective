## Abstract

In modern computer architecture, fixed-width registers impose strict physical limits on the numerical range of integer computations. When an arithmetic operation produces a result that exceeds the register capacity, digital systems undergo arithmetic overflow—a silent truncation and bit-wrap phenomenon governed by modular arithmetic. In two's complement notation, this rollover typically produces an erroneous number with an inverted sign bit. 

This project, **Overflow Detective**, presents an architectural simulator that implements radix conversions, evaluates three standard signed number representations (Sign-Magnitude, 1's Complement, and 2's Complement), and simulates bit-level full-adder arithmetic within an Arithmetic Logic Unit (ALU). The system verifies overflow detection using both the algebraic sign-consistency rule and the hardware carry-bit condition ($V = C_{\text{in}} \oplus C_{\text{out}}$). Both an interactive terminal execution mode and an offline, zero-dependency web dashboard are provided. Comprehensive testing was executed across exhaustive 4-bit combinatorial domains ($256$ cases) and high-bit boundary vectors to validate complete fidelity to physical ALU behavior.

## 1. Introduction and Objectives

### 1.1 Background and Motivation
At the hardware level, arithmetic logic units operate on fixed register widths ($n = 4, 8, 16, 32, 64$). Unlike abstract mathematics where integers are unbounded ($\mathbb{Z}$), hardware integers belong to finite cyclic rings ($\mathbb{Z} / 2^n \mathbb{Z}$). When additions produce numbers outside the representable interval, hardware does not raise a CPU trap by default; instead, it sets a processor status flag (e.g., the `OF` flag in x86 architectures or the `V` bit in ARM architectures) and returns the wrapped modulo value. 

If software fails to inspect the overflow flag, catastrophic system failures occur. Historical examples range from the destruction of the Ariane 5 rocket in 1996 to modern aerospace generator shutdowns and video streaming counter rollovers.

### 1.2 Project Objectives
1. **Algorithmic Radix Conversion:** Implement arbitrary base conversions (Base-10 to Base-2, 8, 16) from first principles using repeated division.
2. **Representation Comparison:** Contrast Sign-Magnitude, 1's Complement, and 2's Complement across word sizes, highlighting range bounds and zero-representation anomalies.
3. **ALU Simulation:** Emulate a ripple carry adder down to individual bitwise logic gates ($A_i$, $B_i$, $C_i$, $S_i$, $C_{i+1}$) tracking carry propagation.
4. **Hardware Overflow Logic:** Formally evaluate and verify the equivalence of the sign-bit inversion rule and the hardware $V = C_{\text{in}} \oplus C_{\text{out}}$ carry rule.
5. **Dual Interface Delivery:** Provide a modular CLI tool for automated verification and an interactive web interface running on Python's built-in HTTP server.

## 2. Theoretical Foundations

### 2.1 Positional Number Systems and Radix Conversion
A non-negative integer $N$ in radix $r$ is represented as a polynomial:

$$N = \sum_{i=0}^{k-1} d_i \cdot r^i$$

where each digit $d_i \in \{0, 1, \dots, r - 1\}$. Conversion from base 10 to base $r$ is accomplished via repeated division by $r$:

$$N = q_0 \cdot r + d_0$$
$$q_0 = q_1 \cdot r + d_1$$
$$\vdots$$
$$q_{k-1} = 0 \cdot r + d_{k-1}$$

The digits are accumulated in reverse order: $N_r = (d_{k-1} d_{k-2} \dots d_0)_r$.

### 2.2 Survey of Signed Number Encodings

#### 1. Sign-Magnitude Representation
- **Structure:** The most significant bit (MSB) denotes sign ($0 = +, 1 = -$). The remaining $n-1$ bits represent the absolute magnitude.
- **Range:** $[-(2^{n-1} - 1), +(2^{n-1} - 1)]$
- **Defects:**
  - Dual representations of zero: $+0 = 0000_2$ and $-0 = 1000_2$ in 4 bits.
  - Requires dedicated subtraction hardware; binary adders cannot directly add negative and positive numbers.

#### 2. One's (1's) Complement Representation
- **Structure:** Positive integers use standard binary. Negative integers are generated by bitwise inversion (NOT) of the positive value: $\bar{A} = (2^n - 1) - A$.
- **Range:** $[-(2^{n-1} - 1), +(2^{n-1} - 1)]$
- **Defects:**
  - Dual zero problem persists: $+0 = 0000_2$ and $-0 = 1111_2$.
  - Requires an extra "end-around carry" adder stage when adding values with different signs.

#### 3. Two's (2's) Complement Representation
- **Structure:** Positive values match standard binary. Negative values are defined as:

$$A_{\text{2's}} = 2^n - A = \bar{A} + 1$$

- **Range:** $[-2^{n-1}, +(2^{n-1} - 1)]$
- **Architectural Advantages:**
  - **Unique Zero:** $+0 = 0000_2$. $-0$ resolves to $\bar{0} + 1 = 1111_2 + 1 = 10000_2 \equiv 0000_2 \pmod{2^n}$.
  - **Unified ALU Hardware:** Subtraction $A - B$ is evaluated directly as $A + (-B) = A + \bar{B} + 1$.
  - **Asymmetric Range:** Exactly one additional negative value ($-2^{n-1}$) is representable.

| Encoding System | 4-bit Range | 8-bit Range | Zero Representation | Subtraction Hardware |
|---|---|---|---|---|
| **Sign-Magnitude** | $[-7, +7]$ | $[-127, +127]$ | Two ($+0, -0$) | Separate subtractor |
| **1's Complement** | $[-7, +7]$ | $[-127, +127]$ | Two ($+0, -0$) | End-around carry |
| **2's Complement** | $[-8, +7]$ | $[-128, +127]$ | Unique ($0$) | Standard adder |

### 2.3 ALU Binary Addition and Overflow Mechanics

A 1-bit full adder computes sum $S_i$ and carry-out $C_{i+1}$ from inputs $A_i, B_i, C_i$:

$$S_i = A_i \oplus B_i \oplus C_i$$
$$C_{i+1} = (A_i \cdot B_i) + (C_i \cdot (A_i \oplus B_i))$$

In an $n$-bit ripple-carry adder, carries ripple from $i=0$ (LSB) up to $i = n-1$ (MSB).

#### Formal Overflow Criteria in Two's Complement:
Overflow occurs if and only if the true mathematical sum falls outside $[-2^{n-1}, 2^{n-1}-1]$.

1. **Sign-Bit Consistency Rule:**
   - Case 1: $A > 0$ and $B > 0 \implies A_{n-1} = 0, B_{n-1} = 0$. If $S_{n-1} = 1$, a positive sum wrapped to negative.
   - Case 2: $A < 0$ and $B < 0 \implies A_{n-1} = 1, B_{n-1} = 1$. If $S_{n-1} = 0$, a negative sum wrapped to positive.
   - Case 3: $A$ and $B$ have opposite signs ($A_{n-1} \neq B_{n-1}$). Overflow is physically impossible because the sum strictly lies between $A$ and $B$.

2. **Digital Hardware Carry-Bit Condition:**
   In physical ALUs, overflow flag $V$ is calculated directly from the carry into the MSB ($C_{n-1}$) and the carry out of the MSB ($C_n$):

$$V = C_{n-1} \oplus C_n$$

#### Mathematical Equivalence Proof:
- **Case 1: $A_{n-1} = 0, B_{n-1} = 0$ (Positive Operands)**  
  $S_{n-1} = 0 \oplus 0 \oplus C_{n-1} = C_{n-1}$.  
  $C_n = (0 \cdot 0) + (C_{n-1} \cdot 0) = 0$.  
  Therefore, $V = C_{n-1} \oplus C_n = C_{n-1} \oplus 0 = C_{n-1} = S_{n-1}$.  
  An overflow occurs when $S_{n-1} = 1$, which corresponds exactly to $V = 1$.

- **Case 2: $A_{n-1} = 1, B_{n-1} = 1$ (Negative Operands)**  
  $S_{n-1} = 1 \oplus 1 \oplus C_{n-1} = C_{n-1}$.  
  $C_n = (1 \cdot 1) + (C_{n-1} \cdot 0) = 1$.  
  Therefore, $V = C_{n-1} \oplus C_n = C_{n-1} \oplus 1 = \overline{C_{n-1}} = \overline{S_{n-1}}$.  
  An overflow occurs when $S_{n-1} = 0$ (erroneously positive), which gives $V = \overline{0} = 1$.

- **Case 3: $A_{n-1} \neq B_{n-1}$ (Mixed Signs)**  
  Without loss of generality, let $A_{n-1} = 0, B_{n-1} = 1$.  
  $S_{n-1} = 0 \oplus 1 \oplus C_{n-1} = 1 \oplus C_{n-1} = \overline{C_{n-1}}$.  
  $C_n = (0 \cdot 1) + (C_{n-1} \cdot 1) = C_{n-1}$.  
  Therefore, $V = C_{n-1} \oplus C_n = C_{n-1} \oplus C_{n-1} = 0$.  
  No overflow can ever occur, matching algebraic theory. $\blacksquare$

## 3. Engineering Case Studies

### 3.1 Ariane 5 Flight 501 (June 4, 1996)
- **Root Cause:** A 64-bit floating-point variable representing horizontal drift velocity was converted into a 16-bit signed integer without guard code.
- **Hardware Trigger:** The physical velocity exceeded $32,767$, causing an unhandled hardware integer overflow exception in the Ada software runtime.
- **Impact:** Both primary and backup Inertial Reference Systems crashed. The rocket veered violently off flight path and self-destructed 37 seconds post-launch, causing a direct loss of \$370 million.
- **Remediation:** Explicit bound checking and register expansion to 32/64 bits.

### 3.2 Boeing 787 Generator Control Unit (FAA AD 2015-09-07)
- **Root Cause:** The internal firmware of the Hamilton Sundstrand Generator Control Units tracked uptime using a 32-bit signed integer incrementing every centisecond ($10\text{ ms}$).
- **Hardware Trigger:** Continuous uninterrupted power for:

$$\frac{2^{31} - 1}{100 \times 60 \times 60 \times 24} \approx 248.55 \text{ days}$$

  caused the counter to overflow to $-2^{31}$, triggering a software safety trip that simultaneously took all four main generators offline.
- **Impact:** Complete electrical failure in flight if power was not cycled before 248 days.
- **Remediation:** Mandatory maintenance cycle requiring a complete aircraft power reboot prior to reaching 248 days, followed by firmware patching to 64-bit counter registers.

### 3.3 YouTube "Gangnam Style" View Counter (December 2014)
- **Root Cause:** YouTube originally stored video view counts in a signed 32-bit integer (`INT32`).
- **Hardware Trigger:** The view count exceeded $2,147,483,647$ ($2^{31}-1$). The next increment rolled the counter into negative space ($-2,147,483,648$).
- **Impact:** Incorrect view counts displayed across global caches.
- **Remediation:** Google re-engineered video view count pipelines to use 64-bit signed integers (`INT64`), extending capacity to $9.22 \times 10^{18}$ views.

### 4.1 Core Simulation Engine (`main.py`)
- Written entirely in Python standard library (`sys`, `argparse`).
- Bit vectors are represented as explicit character strings (`"0"`, `"1"`) to allow exact inspection of carries and bit transitions.
- Supports $4$, $8$, $16$, and $32$-bit configurations.
- Features three execution modes:
  - `--demo`: Prints full structured demonstrations of all sections.
  - `--interactive` (`-i`): Command-line prompt for interactive conversions and additions.
  - `--test` (`-t`): Automated test suite.

### 4.2 Web Service Layer (`app.py`)
- Employs Python's built-in `http.server.HTTPServer` and `BaseHTTPRequestHandler`.
- Operates without any external frameworks (no Flask, Django, or FastAPI required).
- Serves static assets and provides RESTful endpoints:
  - `GET /convert?n={val}&bits={width}`: Returns binary, octal, hex, and signed representations.
  - `GET /add?a={val}&b={val}&bits={width}`: Computes bitwise sum, carry chains, and overflow flags.
  - `GET /bugs`: Returns historical case study metadata.

### 4.3 Web Dashboard Interface (`index.html`)
- Clean, semantic HTML5 and vanilla JavaScript with zero external CDN dependencies (works entirely offline).
- Includes dynamic bit-cell visualization where sign bits and carry bits are clearly color-coded.
- Implements responsive styling supporting both light and dark system color schemes.

## 5. Verification and Experimental Results

### 5.1 Combinatorial 4-Bit Exhaustive Testing
To verify algebraic correctness, an exhaustive combinatorial test was conducted across all pairs of 4-bit signed integers in $[-8, +7]$:

$$\text{Total Test Pairs} = 16 \times 16 = 256$$

For every pair $(A, B)$, the simulation output was checked against mathematical truth:
1. Expected sum: $Sum_{\text{true}} = A + B$.
2. Expected overflow: $\text{Overflow} \iff Sum_{\text{true}} < -8 \lor Sum_{\text{true}} > 7$.
3. When no overflow occurred: $\text{Result}_{\text{sim}} \equiv Sum_{\text{true}}$.
4. Both overflow conditions ($C_{in} \oplus C_{out}$ vs. sign rule) were asserted to match on 100% of iterations.

**Result:** $256 / 256$ cases passed ($100\%$ accuracy).
